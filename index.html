01 / The decision

A familiar capacity problem. An unfamiliar stack.

We had a WordPress brochure site for a business unit within Topflight Travel Group that did not use our in-house development team. Our engineers work in Java and React. It had been hard to justify taking them away from that work to work in PHP and WordPress.

We were considering an agency. Instead, I built an agentic development pipeline using Claude Code, GitHub Actions and Jira, so we could take on the work in-house.

The starting point was an existing site with a custom theme, custom plugins and a backlog of content, layout and maintenance work. This was not a blank-page demo. WordPress also stores much of a site's state in its database, so editing files alone would not be enough.

Claude writes the code. I own the decisions about what we build, whether the result is right and what goes live.

02 / The workflow

A ticket in. Evidence back.

I write a Jira ticket with one visible change, assign it to the agent and review what comes back. GitHub Actions runs Claude Code, prepares the pull request and creates a preview. The agent's task is to produce a reviewable change, not to decide what should go live.

  1. 01 / PERSONBriefJira ticket
  2. 02 / PROCESSBuildClaude Code
  3. 03 / PROCESSCheckDisposable site
  4. 04 / PERSONReviewPreview + evidence
  5. 05 / PERSONReleaseHuman decision

The pipeline automates the work between the brief and review. A person still owns acceptance and release.

Each pull request gets a review pack comparing the starting point with the proposed change. It includes screenshots, browser checks and a risk rating. A preview lets me inspect the branch in a working site before merging it.

  1. 01 / PERSONSpecifyOne change per ticket
  2. 02 / PROCESSImplementWorkflow prepares branch
  3. 03 / PERSONInspectReview the actual result
  4. 04 / PERSONRevise or mergeFeedback or acceptance

If the result is wrong, feedback starts a revision. Passing a check is not the same as satisfying the ticket.

03 / The boundaries

Automation without handing over the release.

The agent does not get production credentials or deploy the live site. I review and merge changes, read database migrations and control releases. The business team approves the wording.

Development, preview, staging and production have different purposes. Keeping them distinct gives both the agent and the reviewer somewhere to inspect a change before it reaches the live site.

  1. 01 / PROCESSAgentPropose code changes
  2. 02 / PERSONReviewerJudge the result
  3. 03 / PERSONBusinessApprove wording
  4. 04 / PERSONRelease ownerDecide what goes live

These are responsibility boundaries, not a claim of autonomous operation or a security audit.

  1. 01 / PROCESSSandboxDisposable test copy
  2. 02 / PERSONPreviewInspect one branch
  3. 03 / PERSONStagingReview merged work
  4. 04 / PERSONProductionControlled release

A preview is for inspecting a proposed change. Staging brings accepted work together before release.

04 / The turning point

The agent needed a way to see.

The first version could edit theme code and check PHP syntax, but it could not run WordPress or see the result. That left me doing the visual testing.

The next phase gave it a disposable copy of the site, screenshots and tools to inspect layout. That expanded the work it could take on much more than another instruction to be careful would have.

A failure worth keeping

Low risk. Still not fixed.

One layout fix received a Low-risk rating but had not visibly fixed the problem. The ticket suggested the wrong cause, and the agent followed it. Its inspection tools also could not open the affected page at that point.

I expanded the tools so it could inspect any page and report what the browser was actually doing. The diagnosis then had to be checked against the evidence, rather than accepted because it was in the ticket.

Another fault appeared in Safari but not in the agent's Chrome-based checks. Photos, design taste and interactive behaviour also needed human judgement. The review process had to reflect those limits.

A risk rating tells me about the checks that ran. It does not tell me that the requested change works.

05 / Beyond code

Content changes need a review trail too.

Page text, menus and other settings can live in the WordPress database. I added a migration process so the agent could propose those changes as scripts rather than leaving them as untracked manual edits.

A migration is tested on the disposable copy, reviewed by a person and applied through the release process. It must be safe to run again. That matters when a deployment is retried or content is copied between environments.

  1. 01 / PROCESSWritePropose a script
  2. 02 / PROCESSRehearseDry run, apply, recheck
  3. 03 / PERSONReadHuman reviews script
  4. 04 / PERSONApplyThrough release process

The database change becomes part of the proposed work, with evidence and review alongside the code.

Built around failures, not a grand reveal.

The detailed project record runs to 11 November 2026, with later status notes through 23 November.

Put decisions where the agent reads

Early runs stopped because the current decision was in a Jira comment while the description still said not to start. The brief had to contain the decision, not just point towards a discussion.

More parallelism was not always better

Changes to shared files collided. Sequencing related tickets helped. Removing a manually updated asset-version line also removed a recurring source of conflicts.

Make uncertainty visible

When the available tools could not prove something, that needed to be stated. Otherwise the reviewer could mistake a missing check for a successful one.

Keep the result in view

A technically valid change can still look wrong. Live previews and concrete design options were more useful than repeated attempts to describe taste in a ticket.

The pull-request total includes pipeline infrastructure and revisions. It is not a count of features, successful agent runs or work completed by the agent alone.

A like-for-like cost of ownership

For work we were considering outsourcing, agency quotes put the cost of ownership at about €120k over five years: roughly €30k for the initial build, and the rest for maintenance and upgrades. These are quoted figures, and likely typical for this kind of site.

~€120koutsourced, over 5 years. About €30k to build, the rest maintenance and upgrades (agency quotes)
<€50agentic credits spent so far (about $50 USD), covering the build and the maintenance and upgrade work to date

The two figures cover the same scope: build, maintenance and upgrades. They differ in time horizon (five years quoted, a few weeks of actual spend) and in what is counted. The credit figure excludes my own review and approval time, which is real and which I did not measure. Every change still passes through a human approval step.

The record includes several dozen merged agent tickets covering homepage changes, menus, responsive fixes, galleries, redirects and content cleanup. As of 23 November 2026 the wider site update was on staging, pending business review. This case study makes no claim about its release.

I did not record enough review-time or time-saved data to calculate a reliable productivity multiple, and the cost comparison above is not one. Commit and pull-request counts cannot answer those questions. The concrete result is a development process our team can own for work we were considering outsourcing. The code is generated, but the responsibility is not outsourced to the model.

08 / What I take from it

Extra capacity is a choice about what comes next.

I understand the concerns about AI's effect on jobs, the environment and people's futures. This project does not settle them.

It does give me a practical alternative to treating every productivity gain as a reason to reduce headcount. Our team can take on work that would otherwise leave it. If an engineer's return on investment increases, perhaps the next question should be what more engineers could build.

For me, the engineering work was in making the output inspectable, making the limits visible and deciding where a person still needed to make the call.

What I would build next

The same approach extends beyond engineering tickets: an SEO and content pipeline, with Content, QA, Security and SEO agents working on tickets raised directly by the marketing team. As with the development pipeline, a person would still review and approve each change before it ships.

Where I think brochure sites go

This is a view, not a result from this project. I expect many static brochure sites to stop needing a CMS. WordPress and similar database-driven content tools can be replaced for simple sites by plain client-side websites, with all editing done by AI at code level. The site owner asks for a page to be created or changed against a brief or ticket, and the change is reviewed like any other.

That would simplify what I built considerably, provided nobody needs hands-on CMS editing.

AI as a multiplier for a team.
Not a reason to stop investing in one.
